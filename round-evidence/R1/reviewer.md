## 本轮考点

I1 从这一轮开始正式计分：**累计成功退款不得超过实付金额**，且 R1 明确
"只有成功退款才计入累计"。这一条直接排除了"申请时就把额度扣掉"的做法。

## 人工评审要点

| 看什么 | 判定依据 |
| --- | --- |
| 是否真的支持多个 AfterSale | 一个订单下能建多条售后，且互不覆盖 |
| 累计口径放在哪里 | 应当在"执行退款成功"时累加，而不是申请时就累加 |
| 是否区分"申请金额"与"已退金额" | 订单上要有独立的已退金额字段或等价的流水求和 |
| 是否增量修改 | R1 明确"不要重写无关代码"；把整个项目推倒重来属于负面信号 |
| 边界 | `refund_amount <= 0` 是否被拒 |

## Golden Answer 观察

- `orders.refunded_amount` 是权威计数器；`CHECK (refunded_amount <= paid_amount)` 是数据库级兜底。
- 额度在**认领退款尝试**时以单条带条件的 `UPDATE` 预留，失败时回退——
  因此"只有成功退款计入"在静止状态下成立，并发下也不会被绕过。
- `test_single_refund_larger_than_paid_amount_is_rejected` 覆盖了 R1 的边界角。

## 常见踩坑

- 申请时就累加额度 → 一笔失败退款永久占额度（T05 会杀）。
- 用 `float` 累加金额 → 0.01 无法精确表示，累加后可能越过上限（T01/T03/T04 会杀）。
- 只在应用层判断而不落库 → 并发下失效（T14 会杀）。
