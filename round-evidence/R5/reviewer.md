## 本轮考点

解释题**不能靠写得好拿分**，只能靠"说得对"。判定方法：把模型的自述逐条与真实代码对照。
本轮没有业务断言型自动化测试，因此 `test-result.txt` 记录的是代码检视输出（真实执行），
人工核对自述与代码是否一致。

## 人工评审要点

| 看什么 | 判定依据 |
| --- | --- |
| 状态机描述 | 是否与代码里的转换表逐条一致；有没有编造状态 |
| 允许退款的条件 | 是否准确说出"`APPROVED` / `REFUND_FAILED` 才能发起尝试" |
| 幂等机制 | 说的是不是代码里真正用的机制 |
| 累计金额机制 | 是否指出计数器 + 条件更新的位置，而不是泛泛说"做了校验" |
| 多 worker | 说出的机制是否真的跨进程有效 |
| 限制 | 是否主动承认崩溃窗口 / SQLite 写锁 / 无分布式事务 |
| **不一致是否自我披露** | R5 明确要求"如与预期不一致请指出"；发现不一致却不说，属于 FAIL |

## Golden Answer 观察

代码检视输出（`test-result.txt`）逐条列出转换表、额度守卫、部分唯一索引与
`BEGIN IMMEDIATE`，README §4/§7 的说明与之逐句对应。

## Rubric 判定提示

`CU-03` 判 PASS 的条件不是"解释完整"，而是"解释与代码一致"。
任何一处把机制说错（例如声称用了 Redis 分布式锁、声称用了 outbox），判 FAIL。
