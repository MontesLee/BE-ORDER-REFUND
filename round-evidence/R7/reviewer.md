## 本轮考点

两组要求，都必须**只修真实问题**：

- 安全：越权读取他人订单/售后、普通用户绕过审核执行退款、异常请求绕过金额限制。
- 性能：N+1、重复查询、退款量增长后的查询退化、长事务、无界加载。

第二轮性能要求刻意不给具体数字，除了"不要求 QPS 压测"——考察的是模型能否识别
**真实存在的**问题并克制地修。

## 人工评审要点

| 看什么 | 判定依据 |
| --- | --- |
| 越权响应码 | 403 或 404 都可接受；**404 更优**（不泄露资源是否存在） |
| 是否只校验存在性 | "查到就返回"是失效模式 #9，必须同时校验归属 |
| 退款执行是否受保护 | 普通用户不能把未审核的申请直接推到渠道 |
| 是否有安全 regression | 应有可执行的越权用例，而不是只改代码 |
| 性能是否真被修 | 索引是否落在真正的热路径；分页是否真的生效 |
| 是否无意义优化 | 加缓存/连接池/"优化 SQL"却没有证据属于负分 |
| 事务边界 | 外部调用是否被放在事务外（长事务问题） |

## Golden Answer 观察

- `auth.assert_can_view`：非本人且非 `AGENT` → 抛 `NotFound`，映射为 404。
- `approve` / `execute` 先过 `require_agent`，普通用户在进入业务逻辑前就被拒绝。
- 索引：`ix_orders_user`、`ix_after_sales_order`、`ix_refunds_order`、`ix_refunds_after_sale`。
- 分页：`limit` 默认 50、上限 100；`limit=5` 对 300 行数据返回 5 行。
- 第三方调用在事务之外，写事务都很短。
