## 关键设计决策

- **存储**：进程内内存字典。需求是"最小可运行"，引入 SQLite/ORM 属于过度设计；用线程锁保证单进程并发安全即可。
- **状态机**：
  - 订单：`CREATED → PAID → REFUNDED`（预留 `CLOSED` 未接入口）。
  - 售后单：`PENDING → APPROVED → REFUNDED` 或 `PENDING → REJECTED`。
  - 仅 `PAID` 订单可申请售后；同一订单仅允许一个进行中（PENDING/APPROVED）的售后单，被拒后可重新申请；仅 `APPROVED` 可执行退款；退款成功后订单状态联动为 `REFUNDED`。
- **错误语义**：不存在 → 404，状态冲突（重复支付、未审核就退款、重复申请等）→ 409，参数校验失败 → 422（FastAPI 默认）。
- **金额**：`Decimal` 避免浮点误差；退款金额直接取订单金额（全额）。
- **API 形态**：资源子路径风格——售后挂在订单下创建（`POST /orders/{id}/refunds`），审核/执行挂在售后单上（`POST /refunds/{id}/review|execute`），查询订单时把关联售后单一并返回，一次请求满足"查询订单和售后状态"。
- **分层**：models / service / main 三层，路由只做参数转发与异常映射，业务规则集中在 service，便于后续换持久化实现。

## 不确定之处

- 「审核售后申请」的接口契约未指定：我采用 `POST /refunds/{id}/review` + `{approve: bool}`，而不是分设 approve/reject 两个端点。若后续轮次给出统一接口契约，可能需要调整路由/字段名。
- 订单号/售后单号格式（`ord_`/`rfd_` 前缀 + 12 位 hex）是自定的，外部契约若要求纯自增 id 需改。
- 退款金额字段是否需要在响应中始终等于订单金额、以及 REJECTED 售后单是否算"售后状态查询"的一部分，均按直觉处理（都返回、都可见）。
- 未实现取消订单（CLOSED 状态仅作枚举预留），需求未要求。
