## 关键设计决策

1. **状态机**：订单 `PENDING_PAYMENT → PAID → REFUNDING → REFUNDED`；售后 `PENDING_REVIEW → APPROVED → REFUNDED` 或 `→ REJECTED`。驳回后订单回退到 `PAID`，允许用户再次发起售后（这是我自行决定的行为，需求未明确）。
2. **全额退款**：`refund_amount` 直接取订单 `total_amount`，不做部分退款。
3. **重复售后限制**：存在待审核/已通过/已退款的售后时禁止重复发起（已驳回的不算），防止一笔订单退两次。这也是需求未写、我按业务常识补的规则。
4. **"执行退款"为同步模拟**：直接改状态 + 记 `refunded_at`，不对接真实支付网关，符合"最小可运行"的定位。
5. **存储**：单进程内存 dict + threading.Lock，不做持久化；进程重启数据清空，README 中已注明。
6. **异常映射**：业务规则冲突（非法状态流转）→ 409，资源不存在 → 404；在 main.py 的 `_handle` 里统一转换，service 层不依赖 FastAPI。
7. **金额**：浮点数计算，合计 `round(, 2)`；README 里注明生产环境应改为整数分。

## 识别到的问题 / 不确定之处

1. **驳回后重新申请再驳回再申请**：理论上可无限循环（每次驳回订单回 PAID）。未加频控，最小版本可接受，但值得注意。
2. **并发安全是浅层的**：Store 只对 dict 写加了锁，"检查订单状态 + 修改"不是原子的（例如两个请求同时支付/同时发起售后存在竞态）。单机演示够用，生产需要把状态流转放进临界区或用数据库事务。
3. **审核/退款无权限控制**：需求说"客服审核"，但没提账号体系，所有接口都是匿名的，任何人都能调用审核接口。按"最小可运行"未做鉴权。
4. **金额浮点精度**：`39.9 * 2` 之类的计算已 round，但更严格的做法是整数分。已在 README 注明。
5. **需求里"查询订单和售后状态"**：我实现为 `GET /orders/{id}`（响应内嵌该订单的售后列表）和 `GET /after-sales/{id}` 两个接口，没有做分页/列表查询——最小版本的理解。
6. **不确定 REJECTED 售后是否应该保留在订单的 after_sales 里**：我选择保留（便于追溯），因此订单查询能看到历史驳回记录。
